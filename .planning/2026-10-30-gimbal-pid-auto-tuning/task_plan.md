## Decisions Made
- 规划阶段仅讨论候选底座；最新用户“Implement the plan”已确认软件实施，使用固定版本BayesianOptimization提议/注册式接口，实机授权仍分Gate B/C。
- 第一轮确认：单工况自动整定；先限制回弹，再缩短稳定时间。
- 用户希望程序自动改变 target 完成实验，不依赖每轮人工拨动；已解释相同位置误差不等于积分、速度、微分历史等初始状态相同。
- 第二轮确认：手拨时始终使能；采用分级准入、监护下自动跑批；性能指标先测基线后确认。以上为设计选择，不授权当前操作硬件。
- 实施前静态核对：USART3 IRQ原走Bridge_Receive_USART；SafetyMode在Bridge_Send_Motor中为总线电机发送零指令，不等于主动保持或机械制动，不能盲目用于整臂故障处理。调参模式现已隔离旧串口路径。
- 第三轮确认：关节0有支撑和安全行程，可承受双机零输出及惯性滑行；具体停止距离/边界在准入时核实。
- 其他关节保持固定安全姿态，保留原控制；不可全局断力。
- Python独占调试串口，统一收发并向VOFA转发数据。
- 允许保护、积分抗饱和和参数无扰切换改进；分阶段测量原始基线、逐项修正对照、修正后BO基线。
- 第四轮确认：故障锁定，人工重新授权；重连不续跑；普通停止和正常单轮结束也将关节0双机零输出（不主动保持）。
- 参数与日志存PC，候选仅设备RAM试用，人工验收后发布；首版不做Flash写入。
- Windows测试机运行Python和VOFA，用户负责烧录和实机验收。
- 已确认Keil工程mdk/infantry.uvprojx，目标STM32F427II，uAC6=0；未执行编译。
- 第五轮确认：批次内允许自动准备起点；调参固件上电关节0默认零输出、明确启动才使能；CLI+配置+VOFA；安全边界、搜索范围、预算等必填校验，缺失拒绝实机。
- 最终技术设计和A–F实施步骤见 docs/gimbal-pid-implementation-plan.md；已获软件实施确认，操作/验证边界见 docs/gimbal-pid-tuning-runbook.md。

## Errors Encountered
- 首次目录检查中项目 `.pi/agents` 不存在使组合 `ls` 返回 1；全局 implementation 角色存在且无 model pin，不影响源码工作。
- C 核心首轮测试：条件积分反向饱和案例的测试期望错误（负误差仍进一步推动负饱和，应冻结积分）；已修正为真正可积分/解饱和的测试条件并通过。
- 原始 PID 逐样本对照发现 P+I+D 与 (P+D)+I 的浮点运算顺序差别，已按原顺序修正并通过位置/速度各1000样本。
- ARM GCC 目标语法检查：portable core 初始通过；STM32接入被项目原有 RVDS/ARMCC inline asm、Gyroscope 隐式类型及 protocol.h 重复成员阻挡。不是 Keil ARMCC5 编译结果；不修无关平台债务，另建 Windows 验收阻塞项。
- 加严 portable core ARM GCC `-Wall -Wextra -Werror` 后出现 CRC 条件表达式符号性告警；已将移位明确为 uint32，保持CRC算法不变并重跑。
- 根目录初次运行Python测试未指定PYTHONPATH导致3项导入错误；正确包路径下31项通过。
- 真实C→评分集成初次3处失败：最终RUN已disabled/zero，但评分误要求全RUN使能；已统一端点策略并通过5/5真实C回归。END_BATCH的batch_id清零契约同时对齐。
